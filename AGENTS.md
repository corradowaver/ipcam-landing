# Правила разработки ipcam-landing

## Назначение и границы проекта

Проект — адаптивный сайт на React + Vite, рассчитанный на 3–6 страниц или разделов.
Состав страниц, контент и визуальное направление уточняются отдельно. Не придумывай
характеристики продукта, цены, отзывы, клиентов или работающие интеграции.
До утверждения содержания поддерживай минимальную рабочую основу.

Этот файл действует на весь репозиторий. Перед изменениями прочитай его, проверь
`git status` и существующие решения. Сохраняй изменения пользователя.
Общайся с пользователем по-русски; код, имена файлов и идентификаторы пиши по-английски.

Перед применением прочитай соответствующий `SKILL.md` из каталога доступных навыков.
Не копируй кеш плагинов и пути конкретного компьютера в исходники сайта.

## Визуальное направление: редакционный индустриальный дизайн

Актуальные источники истины — `mockup-cozy/index.html`,
`mockup-cozy/index-dark.html`, `docs/design-baseline.md` и `docs/color-themes.md`.
Все пять страниц React-приложения перенесены из этих макетов. Светлая и тёмная
темы используют общие смысловые токены; по умолчанию учитывается тема устройства,
ручной выбор сохраняется. Макеты остаются визуальными эталонами.
До отдельного согласования сохраняй название
«Вместе», пять страниц, основное действие «Запросить демо» и слоган:

> Давайте посмотрим. Вместе.

Используй минималистичный интерфейс, крупные простые формы, скругления
28 px у карточек и 16 px у кнопок. Иллюстрации поддерживают смысл секции и не
заменяют текст. Не вставляй реальные скриншоты продукта, декоративные коллажи и
лишние детали.

Палитру #F49097, #DFB2F4, #F5E960, #F2F5FF и #55D6C2 используй
функционально: для основных действий, статусов, выделения AI и крупных акцентов.
Не окрашивай каждый блок и не используй жёлтый, розовый или мятный для мелкого
текста на светлом фоне. Основные текст, линии и большие поверхности остаются
нейтральными.

Светлая тема использует фон #F6F7FB и мягкие секции #F2F5FF; тёмная — фон
#171A22 и поверхности #202530. Пастельные акценты сохраняются в обеих темах.
Текст на них остаётся тёмным (#293342). Для больших AI-подложек используй
#F0E6F7 / #302B3D. Тёмный маркер заголовка: жёлтый текст на #3A3826.
Общие цветовые роли находятся в `mockup-cozy/shared/themes.css`; обе версии
собираются командой `node scripts/build-mockup.js` из одних исходников.

Фотографии макета должны выглядеть как кадры качественной стационарной камеры
видеонаблюдения: верхний наклонный ракурс, нейтральные цвета, естественный свет.
Люди заняты работой, не позируют и не улыбаются. Синтетические кадры подписывай
как демонстрационные изображения, созданные ИИ. Рамки обнаружения и подписи
накладывай отдельным UI-слоем, чтобы менять их независимо от фотографии.
Главная сцена сохраняет
производственную линию, коробки и трёх сотрудников: каски отмечаются сплошными
мятными рамками, отсутствие каски — розовой пунктирной рамкой. Вторая схема
сохраняет последовательность «камера → AI-анализ → интерфейс наблюдения».

Поддерживай выразительную редакционную композицию внутри общей сетки:

- на первом экране текст занимает около половины ширины, иллюстрация — вторую;
  на узком экране иллюстрация располагается после действий;
- меняй ритм секций контролируемой асимметрией: чередуй широкие и компактные
  элементы, смещай соседние блоки, но сохраняй порядок чтения и общие отступы;
- жёлтым маркером выделяй нижнюю половину одного последнего смыслового слова в
  `h1`; выделение не должно пересекать соседнюю строку или появляться в `h2`;
- оставляй по одной конкретной мысли на второстепенный текст, убирай повторы и
  внутренние термины проектирования из пользовательского интерфейса;
- основной поясняющий текст набирай размером 14–16 px; 11–12 px используй только
  для необязательных меток, статусов и нумерации.

## Актуальные и воспроизводимые технологии

- Используй актуальные стабильные, поддерживаемые и взаимно совместимые версии.
  Перед добавлением или обновлением сверяй официальную документацию, npm registry,
  `engines`, `peerDependencies` и изменения API. Не выбирай версии по памяти.
- Node.js — актуальная LTS-ветка. Точная версия находится в `.node-version`.
  npm — единственный менеджер пакетов; его версия указана в `package.json`.
- Прямые зависимости фиксируются точными версиями. `package-lock.json` храни в Git;
  воспроизводимая установка — `npm ci`. Не редактируй lockfile вручную.
- Не используй alpha, beta, RC, canary, неподдерживаемые API, `--force` или
  `--legacy-peer-deps` для обхода несовместимости.
- Если самая новая версия не поддерживается инструментами, используй самую новую
  совместимую стабильную и запиши причину в `docs/dependencies.md`.
  Возвращайся к ограничению при обновлении зависимостей.
- Не обновляй весь стек попутно с правкой текста или CSS. Обновление — отдельное
  осмысленное изменение с проверками и обновлением документации версий.
- TypeScript работает в strict-режиме. Не отключай проверки ради прохождения сборки.
- Базовый набор: React, Vite, TypeScript, CSS Modules, ESLint, Prettier, Playwright.
  Новая библиотека должна решать уже существующую задачу. Не добавляй заранее
  глобальное хранилище, DI-контейнер, универсальный HTTP-клиент или UI-фреймворк.

## Архитектура и независимость модулей

Используй простую модульную архитектуру с группировкой по назначению:

```text
src/
  main.tsx                 # запуск React, подключение глобальных стилей
  app/                     # композиция приложения, провайдеры, маршруты
  pages/<page>/            # независимая страница и её локальные разделы
  features/<feature>/      # самостоятельный пользовательский сценарий, при появлении
  shared/ui/<component>/   # действительно общие компоненты
  shared/lib/<purpose>/    # небольшие общие функции и инфраструктурные адаптеры
  shared/styles/          # общие токены и базовые стили
tests/e2e/                # проверки поведения сайта
docs/                     # решения и инструкции
```

Не создавай пустые слои и каталоги для будущих возможностей. Направление импортов:
`app -> pages -> features -> shared`; верхний слой может пропускать промежуточные.

- `shared` не знает о страницах, функциях продукта и маршрутах приложения.
- Страницы не импортируют другие страницы; features не импортируют другие features.
  Объединяй независимые модули в вышестоящем слое. Циклические зависимости запрещены.
- Между модулями используй небольшой публичный API через `index.ts` и алиас `@/`.
  Внутри модуля — относительные импорты. Не делай общий barrel-файл для всего проекта.
- Каждая страница или функция владеет своими компонентами, типами, данными, стилями
  и локальными ассетами. Поднимай их в `shared` только при реальном переиспользовании.
- Компоненты получают зависимости и данные через props или явные функции.
  Не используй скрытые глобальные объекты, изменяемые синглтоны и побочные эффекты импортов.
- Маршруты и пункты навигации собираются в `app`, когда появятся отдельные страницы.
  Используй один источник метаданных маршрутов; не дублируй URL по компонентам.
- Удаление страницы должно требовать удаления её каталога, регистрации маршрута,
  пункта навигации и относящихся к ней тестов/ассетов. Общие компоненты и соседние
  страницы не должны требовать переписывания. Проверяй оставшиеся ссылки и импорты.
- Секции лендинга компонуются явно внутри страницы. Удаление секции требует удаления
  её подключения и якоря меню, но не изменения внутренней логики соседних секций.
- Не строй универсальную CMS, систему плагинов или полную многослойную enterprise-
  архитектуру ради нескольких страниц. Применяй паттерны там, где они уменьшают связи.

## Clean code, SRP и DRY

- У каждого файла, компонента, hook, функции и класса должна быть одна ясная
  ответственность и одна основная причина изменения. God-class, god-component
  и файлы, совмещающие UI, сетевые запросы, валидацию и бизнес-логику, запрещены.
- Предпочитай функции, функциональные React-компоненты и композицию. Класс-помощник
  допустим, если ему нужны состояние или жизненный цикл; набор статических функций
  оформляй небольшим модулем, а не классом ради класса.
- Перед добавлением логики ищи похожую реализацию через `rg`. Перед сдачей повторно
  просмотри изменения на дублирование правил, преобразований, запросов и разметки.
- Обнаруженную общую логику выноси в функцию, hook, компонент или узкий адаптер.
  Одинаковое правило должно иметь один источник истины. Данные, которые отличаются
  только значениями, задавай типизированной конфигурацией.
- Абстракция должна описывать общее поведение. Не объединяй разные по смыслу правила
  только из-за похожего синтаксиса; не заменяй дублирование универсальным компонентом
  с десятками флагов. Если общей логики нет, сходство строк само по себе не нарушение DRY.
- Избегай безымянных `utils.ts`, `helpers.ts`, `common.ts`: называй модули по задаче,
  например `format-price.ts`, `validate-contact.ts`, `logger.ts`.
- Пиши короткие связные функции, ранние возвраты, понятные имена и явные контракты.
  Глубокая вложенность и несколько обязанностей — повод разделить код.
  Файл около 300 строк или функция около 60 строк требуют пересмотра ответственности,
  но не механического разбиения на бессмысленные обёртки.
- Не используй `any`, двойные приведения через `unknown`, подавления TypeScript/ESLint
  без локального обоснования. На внешних границах принимай `unknown` и сужай тип.
- Комментарии объясняют причины и ограничения. Удаляй мёртвый код, временные заглушки
  и закомментированные реализации; не оставляй незадействованные абстракции.

## React, стили и доступность

- Состояние хранится как можно ближе к месту использования. Производные значения
  вычисляй из данных; не синхронизируй их через лишние state/effect.
- Effects используй для внешних систем, с необходимой очисткой. Не делай запросы
  или другие побочные эффекты в render. `memo`, `useMemo`, `useCallback` добавляй
  по измеряемой причине, а не к каждому компоненту.
- CSS Modules изолируют стили модулей. Глобально допустимы базовые правила и токены.
  Не стилизуй чужие внутренние классы; повторяющиеся цвета и размеры выноси в токены.
- Используй семантический HTML, правильные заголовки, подписи полей, видимый фокус,
  управление с клавиатуры, доступные имена и `prefers-reduced-motion` для анимаций.
- Проверяй узкий экран от 360 px и desktop. Навигация должна работать без hover.
  Изображения должны иметь размеры, осмысленный alt или пустой alt для декора.
- Не вставляй непроверенный HTML. В клиентском коде и переменных `VITE_*` нет секретов.
- Когда появятся отдельные страницы, обеспечь прямое открытие URL, reload, back/forward,
  страницу 404 и настройку SPA fallback на выбранном хостинге. SEO-метаданные должны
  соответствовать реальному содержанию; стратегию индексации выбирай до публикации.

## Ошибки и логирование

- Все реальные ошибки приложения должны иметь владельца обработки и быть залогированы.
  Используй единую точку `shared/lib/logger`. Не разбрасывай `console.*` по коду.
- Логируй один раз там, где есть контекст и принимается решение: показать fallback,
  сообщить о неудаче операции или передать ошибку выше. Не делай catch-log-rethrow
  на каждом слое. Пустые catch и выдача успеха после сбоя запрещены.
- Ошибки рендера обрабатывает Error Boundary; React root сообщает о пойманных,
  непойманных и восстановленных ошибках в logger. Необработанные Promise rejection
  фиксируются отдельно. Сбой независимого интерактивного блока изолируй локальной
  границей, если это позволяет остальной странице оставаться полезной.
- Сетевые ошибки, ответы API, ввод пользователя и браузерное хранилище проверяй
  на соответствующей внешней границе, когда эти интеграции появятся.
  Не окружай каждую функцию try/catch и не перепроверяй типизированные внутренние
  данные на каждом шаге. Защитная ветка должна соответствовать реальному сценарию.
- Невалидное поле формы, отмена пользователем и ожидаемый abort — обычные состояния,
  а не аварии. Покажи понятную обратную связь, не создавай error-спам.
- Запись ошибки содержит стабильный код события и пригодную для диагностики ошибку.
  Дополнительный контекст разрешён только из явно безопасного набора полей.
  Не логируй формы, персональные данные, токены, cookies и полные HTTP payload.
  Перед логированием ошибок внешних сервисов исключи чувствительные данные из message/stack.
- Пользователю показывай понятное сообщение и доступное действие восстановления;
  технический stack trace остаётся в диагностике. Отправку логов во внешний сервис
  добавляй при выборе сервиса и настроек, не выдавай console-лог за удалённый мониторинг.

## Проверки и рабочий процесс

1. Прочитай задачу, состояние Git и затрагиваемые модули. Найди уже существующую
   общую логику и выбери минимальную область изменения.
2. Для нового дизайна сначала используй контекст и референсы пользователя;
   при необходимости обсуди варианты через visualize. Реализацию храни в проекте.
3. Вноси законченные небольшие изменения. Значимые архитектурные решения фиксируй
   в `docs/`; обновляй инструкции вместе с фактическим поведением.
4. Выбирай тест по риску. Чистую сложную логику проверяй unit-тестами, взаимодействия —
   интеграционными, главные пути пользователя — E2E. Не пиши тесты на каждый div,
   статический текст, приватную реализацию или тривиальную обратимую правку.
5. E2E выполняй на production-сборке через Vite preview. Проверяй загрузку, навигацию,
   формы и ошибки по мере их появления. Тесты независимы; реальные отправки заявок
   во внешние системы подменяй на границе теста.
6. Playwright: `getByRole`/`getByLabel`, затем `data-testid`, если семантического
   локатора недостаточно. Используй auto-wait и web-first assertions. Не применяй
   `waitForTimeout`, хрупкие CSS-селекторы, зависимость от порядка тестов и retries,
   скрывающие нестабильность. Page Objects добавляй при реальном повторении сценариев.
7. Минимальная матрица — Chromium desktop и мобильный viewport. Расширяй её Firefox /
   WebKit перед публичным релизом и при изменениях с браузерными рисками.
   Эмуляция размера экрана не доказывает работу на реальном мобильном устройстве.
8. Перед сдачей кода запускай `npm run check`: форматирование, ESLint, TypeScript,
   production-сборка и E2E. Для изменения только документации достаточно
   `npm run format:check` и проверки фактов/ссылок. Изменения UI также осмотри визуально.
9. Прочитай полный результат, код завершения и итоговый diff. Проверь DRY,
   направление зависимостей, удаляемость модуля, отсутствие секретов и лишних файлов.
   Не ослабляй тесты и линтер, чтобы спрятать настоящую проблему.
10. Сообщи, что изменено, какие проверки действительно выполнены и что осталось
    непроверенным. Не заявляй «готово» или «всё работает» по предположению.

## Команды

На Windows с устаревшим системным Node.js сначала выполни в текущем PowerShell:

```powershell
. .\scripts\setup-node.ps1
```

Скрипт включает закреплённый Node.js из `.tools` для текущей сессии; если его нет,
скачивает официальный архив и проверяет SHA-256. Для других ОС используй свой
менеджер Node.js с `.node-version`. Затем:

```sh
npm ci
```
